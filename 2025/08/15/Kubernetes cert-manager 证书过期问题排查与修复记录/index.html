# Kubernetes cert-manager 证书过期问题排查与修复记录

最近在维护公司的 GitLab 服务时，遇到了一次证书过期的问题。趁着这次处理的过程，我把整个排查、修复的过程记录下来，希望对同样在 Kubernetes 中用 cert-manager 管理证书的朋友有所帮助。

# 背景

我们的 GitLab 服务部署在 Kubernetes 集群中，使用 cert-manager 自动管理 TLS 证书。

域名分成两个部分：

  • gitlab.xxxx.net → nginx ingress
  • registry.xxxx.net → Kong ingress

证书签发方式是 Let’s Encrypt + HTTP-01 验证，Issuer 配置为 ClusterIssuer。

# 问题现象

一天访问 GitLab 的 Registry 地址时，浏览器直接报：

证书已过期（NET::ERR_CERT_DATE_INVALID）

检查 GitLab 页面，gitlab.xxxx.net 访问正常，但 Registry 域名的证书已经失效。

我第一反应是 cert-manager 可能续期失败，于是准备排查。

# 排查过程

# 1. 查看证书状态

发现 gitlab-ng-tls 状态是 Ready=True，有效期到 2025-11-12，说明它刚刚续签成功。

但 Registry 对应的证书没有更新，还是旧的到期时间。

# 2. 找到 Challenge 和 solver ingress

这意味着 HTTP 请求被强制跳转到 HTTPS，ACME 验证失败。

# 4. 调整 solver ingress

我针对 GitLab 的 solver ingress 做了三件事：

  1. 指定 ingressClass
  1. 关闭 HTTP → HTTPS 重定向
  1. 删除失败的 Order 重新触发

# 原因分析

通过这次排查，我总结出问题的根本原因：

  • HTTP-01 验证依赖域名的 80 端口直通到 solver pod。
  • 我们的 nginx ingress 默认开启了 HTTPS 强制跳转，导致 ACME 在访问 http://.../.well-known/acme-challenge/... 时被 308 重定向到 HTTPS，从而验证失败。
  • Registry 用的是 Kong ingress，而 Kong 没有正确处理 solver ingress 流量，也可能拦截了 80 端口请求。

最终，GitLab 的证书是我手动调整 ingress 规则后成功续签的；Registry 的证书需要进一步处理 Kong ingress 配置，或者改用 DNS-01 验证。

# 经验总结

  1. HTTP-01 续期需要保证：

    • 80 端口对外开放
    • .well-known/acme-challenge/ 不要跳转到 HTTPS
    • ingressClass 要和实际 ingress controller 匹配

  2. 对多 ingressClass 环境建议：

    • 统一证书签发方式（最好 DNS-01）
    • 或者在 solver ingress 创建时自动 patch ingressClass

  3. 日常监控：

    • 定期跑 kubectl get certificate -A
    • 配合 openssl s_client 检查实际到期时间
